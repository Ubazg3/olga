### H1 ### 1. מבוא ורקע לפרויקט
## H2 ## 1.1 רקע והשראה לפרויקט
הבחירה לפתח את Battle Thunder נובעת מאהבה אישית למשחקים אסטרטגיים בכלל, ולמשחק הצוללות הקלאסי ששיחקתי בתור ילד. הכללים פשוטים, אבל העומק הטקטי עצום. הצירוף של ניחוש, ניהול סיכויים וניסיון לחשוב כמו היריב יוצר חוויה הוגנת ולא צפויה גם אחרי משחקים רבים.
המטרה שלי בפרויקט הייתה לקחת את החוויה הקלאסית הזאת ולהעביר אותה לעידן המודרני: לאפשר משחק רב-משתתפים בזמן אמת דרך הרשת בין שני שחקנים שיושבים על שני מחשבים שונים, להוסיף יריב מבוסס בינה מלאכותית בעל אסטרטגיית חיפוש אמיתית עבור שחקנים בודדים, לנהל מערכת דירוג ELO גלובלית, ולספק את כל זה דרך שלושה לקוחות נפרדים – Desktop (WPF), Web (Blazor), ומובייל (MAUI) – שכולם פונים לאותו שרת ולאותו מסד נתונים.
המערכת בנויה כאדריכלות שרת-לקוח מלאה: השרת אחראי על הלוגיקה, על שמירת הנתונים ועל סנכרון השחקנים, והלקוחות (בכל שלושת הפלטפורמות) הם רק תצוגה ובקרת מצב. כל לקוח ניגש אל השרת באמצעות הפרוטוקול המתאים לו – WCF Duplex עבור לקוח ה-WPF, SignalR ו-REST API עבור לקוחות ה-Web וה-MAUI.
## H2 ## 1.2 שם הפרויקט ותיאורו
שם הפרויקט: Battle Thunder – משחק קרב צוללות רב-משתתפים בזמן אמת.
המערכת היא יישום שרת-לקוח מלא עם תקשורת דו-כיוונית. כל שחקן נרשם, מתחבר, מציב חמש ספינות (Carrier בגודל 5, Battleship בגודל 4, Submarine בגודל 3, ושני Destroyer בגודל 2) על לוח 10×10 הנשמר אצלו ואצל השרת בלבד, ואז מתחיל קרב תורות מול יריב אנושי (Multiplayer) או מול יריב מבוסס בינה מלאכותית (Singleplayer). במהלך המשחק כל ירייה מעדכנת בזמן אמת את שני הצדדים, מתעדכן צבע התא, נשמרת היסטוריית הקרב, נסגרים תורות, ומועברות הודעות צ׳אט בין השחקנים. בסיום נשמרות הסטטיסטיקות במסד הנתונים ומופיעה אופציה לבקש Rematch מהיריב או לחזור לתפריט הראשי. בנוסף מתן ממשק ניהול ((Admin לחסימה וניהול משתמשים.
## H2 ## 1.3 קהל היעד
המערכת פונה לארבעה סוגי משתמשים שונים:
שחקנים פרטיים שאוהבים משחקי אסטרטגיה ימיים – כל גיל, ללא צורך בידע טכני.
שחקנים שמחפשים חוויה מהירה של 10–15 דקות מול יריב חי, מבלי להוריד אפליקציה כבדה.
שחקנים בודדים שרוצים לתרגל אסטרטגיות מול יריב AI חכם המבוסס על אלגוריתם Hunt/Target אמיתי, ולא רק על ירייה אקראית.
שחקנים תחרותיים שמעוניינים לטפס בלוח המובילים הגלובלי באמצעות מערכת דירוג ELO עם 24 דרגות.
## H2 ## 1.4 מטרות המערכת
מטרות על:
יצירת חוויית משחק רב-משתתפים בזמן אמת עם תקשורת דו כיוונית אמיתית מול שרת מרכזי.
בניית יריב AI חכם שמספק אתגר אמיתי גם לשחקנים מנוסים.
הצגת אותה מערכת באמצעות שלושה לקוחות שונים: WPF, Web ו-MAUI המתחברים לאותו שרת ולאותו מסד נתונים.
מתן ממשק נקי, בעיצוב נאוטי כהה ברוח משחקי, עם אנימציות, אפקטים וצלילים.
מערכת דירוג ELO גלובלית עם 6 דרגות (Iron, Bronze, Silver, Gold, Diamond, Master) ו-24 תת-דרגות, לפי המודל המקובל במשחקים תחרותיים.
מטרות נלוות:
הצפנת סיסמאות בעזרת BCrypt עם Salt אקראי למניעת דליפות מידע.
זיהוי אוטומטי של ניתוקי לקוח (קריסת אפליקציה או ניתוק רשת) ושחרור היריב מהמשחק.
מערכת Rematch הוגנת – שני השחקנים חייבים להסכים לפני התחלת משחק חדש.
צ׳אט פנימי בתוך המשחק עם הגבלת אורך הודעה למניעת הצפה.
מערכת הישגים (Achievements) הכוללת תגי Bronze/Silver/Gold.
היסטוריית התחברויות לכל משתמש ויומן ניצחונות מלא.
פאנל ניהול (Admin) המאפשר למשתמשים מיוחסים לצפות בכל המשתמשים, לאפס סטטיסטיקות ולמחוק חשבונות.
## H2 ## 1.5 תיאור כללי של המערכת
המערכת בנויה לפי אדריכלות שכבות נקייה, עם הפרדה מלאה בין שכבת התצוגה, שכבת הלוגיקה ושכבת הנתונים. הבחירה בארכיטקטורה זו מאפשרת לצרף לקוחות נוספים בעתיד מבלי לגעת בקוד השרת או במסד הנתונים, וזאת אכן מה שעשיתי כאשר הוספתי את לקוח ה-Web ולקוח ה-MAUI לאחר שכבר היה לקוח WPF פעיל.
השכבות העיקריות במערכת הן:
שכבת Model – מחלקות נתונים (User, Base, GameStateDto, ShipPlacementDto, AttackResultDto, PlayerStatsDto ועוד) המשותפות לשרת וללקוחות דרך WCF DataContract או דרך JSON serialization.
שכבת ViewDB – שכבת גישה למסד הנתונים, יורשת ממחלקה אבסטרקטית BaseDB שמכילה את הפעולות הכלליות (Select, AddToDB, SaveChanges) עם הגנה מלאה מפני SQL Injection באמצעות פרמטרי OleDb.
שכבת BusinessLogic – לוגיקה עסקית: ניהול משתמשים (UserManager עם תבנית Singleton), הצפנת סיסמאות (PasswordManager עם BCrypt).
שכבת WCF Server – שירות WCF Duplex בפרוטוקול netTcpBinding המשמש את לקוח ה-WPF, יחד עם שני שירותים נוספים בפרוטוקול basicHttpBinding לאימות ולסטטיסטיקות.
שכבת Web Server (Blazor + REST API + SignalR Hub) – שרת ASP.NET Core שמספק את לקוח ה-Web, חושף REST API למשתמשים שאינם דפדפן (כמו MAUI), ומכיל Hub של SignalR למשחק רב-משתתפים בזמן אמת.
שכבת לקוח WPF – ממשק שולחני עשיר, מבוסס Pages עם ניווט באמצעות Frame, אנימציות Storyboard ו-Callback Handlers שמטפלים באירועי השרת.
שכבת לקוח Blazor Web – אפליקציה בדפדפן בעיצוב זהה לזה של הלקוח השולחני, עם תמיכה ב-Add to Home Screen על iOS.
שכבת לקוח MAUI – אפליקציה נטיבית לאנדרואיד (וגם ל-Windows) המשתמשת ב-HttpClient לקריאות REST וב-SignalR Client למשחק בזמן אמת.
## H2 ## 1.6 גבולות המערכת
בכל פרויקט תוכנה חשוב להגדיר במפורש מה כן בתחום ומה לא, כדי לא לקרוס תחת עומס של דרישות. הבחירות שלי היו:
המערכת אכן כוללת:
שלושה לקוחות פעילים: WPF Desktop, Web (Blazor Server), ו-MAUI (Android + Windows).
שני סוגי משתמשים – שחקן רגיל ומנהל (Admin) – כאשר ההבחנה מתבצעת בקובץ AdminConfig עם רשימת שמות משתמש מורשים.
משחק מול בינה מלאכותית ומול שחקן אחר, במצבים מדורגים (Ranked) ובלתי מדורגים (Unranked).
חשיפת השרת לאינטרנט באמצעות שירות מנהור (ngrok), כדי לאפשר משחק מול שחקנים שאינם על אותו LAN.
המערכת אינה כוללת:
הצפנת תקשורת ברמת התווך (TLS/HTTPS) – הקריאות מתבצעות ב-NetTcp/HTTP בסביבת LAN. הצפנה ניתנת להוספה בעתיד דרך הגדרת תעודה.
שמירת היסטוריית הצ׳אט במסד הנתונים – הודעות מועברות בזמן אמת בלבד.
אינטגרציה עם רשתות חברתיות (Google/Facebook Sign-In) או רכישות בתוך האפליקציה.

## H2 ## 1.8 אתגרים מרכזיים בפרויקט
במהלך הפיתוח התמודדתי עם מספר אתגרים מרכזיים. אני מציין כאן את החשובים שבהם, יחד עם הפתרון שמצאתי לכל אחד:
זיהוי ניתוקי לקוח:
לקוח שקורס אינו מספיק לקרוא ל-LeaveGame ולכן השרת אינו יודע שהיריב נעלם. הפתרון: בכל פעם שלקוח מתחבר (JoinGame), אני נרשם לאירועי channel.Faulted ו-channel.Closed שלו, ואם אחד מהם נורה אני משחרר את היריב, מודיע לו, ומנקה את ה-Session. נדרשת הגנה מפני אירועים כפולים (reconnect-safety) כדי שלא תתרחש מחיקה כפולה.
סנכרון תורות בין שני שחקנים:
מי המשחק שלו? איך מודיעים? איך מונעים מצב שבו שני שחקנים יורים בו-זמנית? הפתרון: שדה CurrentTurn ב-GameSession, נעילה (lock) על כל פעולת FireShot, ושימוש ב-OnYourTurn Callback ליריב לאחר כל ירייה.
גלישה לאינטרנט הציבורי:
LAN בלבד לא מספיק כדי לשחק מול חברים מרחוק. הפתרון: שירות ngrok יוצר מנהור HTTPS ציבורי לשרת המקומי. עם דומיין קבוע אני יכול להזמין חברים בכל מקום בעולם להיכנס לכתובת אחת ולשחק נגדי.
## H2 ## 1.9 חידושים ומאפיינים מיוחדים
יש בפרויקט מספר מאפיינים שאינם נפוצים בפרויקטי תיכון:
ארכיטקטורת WCF Duplex עם CallbackContract וניהול Channel Lifecycle.
יריב AI מבוסס Probability Density – לא אלגוריתם אקראי, אלא חישוב הסתברויות שמתעדכן אחרי כל ירייה.
שלושה לקוחות נפרדים (WPF + Blazor + MAUI) המתחברים לאותו שרת ולאותו מסד נתונים.
מערכת SignalR Hub עם IGameClient interface שמאפשרת ל-Blazor users ול-MAUI users להזדווג ולשחק זה נגד זה.
חשיפה ציבורית של השרת באמצעות ngrok, עם דומיין קבוע ב-HTTPS.
מערכת Admin מובנית עם רשימת מנהלים בקוד, עם דף ניהול גרפי שמאפשר צפייה במשתמשים, איפוס סטטיסטיקות ומחיקה.
Logger מקצועי בשרת עם רמות חומרה (INFO/WARN/ERROR), כתיבה לקובץ והדפסה צבעונית לקונסול, וכל פעולת IO עטופה ב-try/catch כדי שלעולם לא תקרוס.
SafeCallback Pattern – פונקציה ייעודית שעוטפת כל קריאת Callback ומונעת מאחת שנכשלה להפיל את כל המשחק.

### H1 ### 3. ניתוח המערכת
## H2 ## 3.1 מסמך ייזום
שם הפרויקט: Battle Thunder – משחק קרב צוללות רב-משתתפים.
בעיה קיימת:
משחק הצוללות הקלאסי מצריך שני אנשים שיושבים פיזית באותו חדר. אין דרך נוחה לשחק משחק רציני נגד חבר שגר רחוק. גם משחקי הצוללות הדיגיטליים הקיימים לרוב פשטניים, אין יריב AI חכם, אין שמירת היסטוריית ניצחונות, אין ניתוקי שחקנים מנוהלים, ואין צ׳אט פנימי.
פתרון מוצע:
מערכת שרת לקוח שמאפשרת לשני שחקנים לשחק קרב צוללות בזמן אמת מכל מקום בעולם, עם תקשורת דו-כיוונית מלאה, יריב AI חכם, מערכת רישום והתחברות מאובטחת, סטטיסטיקות אישיות, לוח מובילים גלובלי, צ׳אט פנימי, ניהול ניתוקים אוטומטי, מערכת Rematch הוגנת, ולקוחות לכמה פלטפורמות שונות.
ערך עסקי:
משחק רב-משתתפים מהיר וממוקד ללא צורך בהורדה של פלטפורמה כבדה.
יריב AI שמאפשר תרגול לבד באופן משמעותי – לא רק תיק חבטות.
שקיפות סטטיסטית – כל שחקן יודע בדיוק כמה ניצח, כמה הפסיד, ומה אחוז הניצחונות שלו.
תחרותיות גלובלית באמצעות לוח המובילים.
גמישות פלטפורמה – לשחק מהמחשב הביתי (WPF), מהדפדפן בכל מקום (Web), או מהטלפון הנייד (MAUI).

## H2 ## 3.5 עץ תהליכים (Process Tree)
עץ התהליכים מתאר את ההזדמנויות שיש לשחקן ברגע נתון, על-פי מצב המערכת. מהשורש (Battle Thunder) מתפצלים שני ענפים עיקריים: אימות וזיהוי (התחברות, רישום, יציאה) ומשחק (מול AI או מול שחקן אחר).
תרשים: עץ תהליכים – Process Tree
שורש: Battle Thunder
ענף 1 – אימות וזיהוי: רישום משתמש חדש → התחברות → תפריט ראשי → יציאה.
ענף 2 – משחק:
        ▸ משחק נגד AI (offline) – הצבת ספינות → קרב מול AI → סיום → תפריט.
        ▸ משחק רב-משתתפים – בחירת מצב (Ranked/Unranked) → המתנה ליריב → הצבת ספינות → קרב → סיום → Rematch או יציאה.
ענף 3 – צפייה בנתונים: לוח מובילים / היסטוריית משחקים / הישגים / היסטוריית התחברויות.
ענף 4 – ניהול (Admin בלבד): רשימת משתמשים → איפוס סטטיסטיקות / מחיקת חשבון / יומן משחקים גלובלי.

### H1 ### 4. בסיס הנתונים
## H2 ## 4.1 בחירת מסד הנתונים
מסד הנתונים של Battle Thunder ממומש ב-Microsoft Access (.accdb), עם גישה דרך OleDb בלבד. הבחירה הזו נובעת משלוש סיבות:
פשטות פיתוח – אין צורך בשרת DB נפרד (SQL Server, MySQL) שצריך להתקין, להגדיר משתמשים ולהריץ כשירות. הקובץ .accdb הוא קובץ יחיד שיושב במחשב, וזה מספיק לפרויקט בקנה מידה זה.
עמידה בדרישות החלופה – המחוון של חלופת "שירותי אינטרנט, תכנות אסינכרוני ומסדי נתונים" מצפה למסד נתונים מנורמל עם פעולות SELECT/INSERT/UPDATE/DELETE ופרמטרים מאובטחים. Access מספק את כל זה דרך OleDb.
ניתן ליצור שאילתות מורכבות, לקבוע מפתחות זרים, ולהשתמש בכל פעולות ה-SQL הסטנדרטיות.
## H2 ## 4.2 פירוט הטבלאות (מילון נתונים)
מסד הנתונים מכיל 7 טבלאות. כל אחת מתעדת היבט שונה של המערכת:
1. UserDataTable – טבלת משתמשים
מאחסנת את פרטי המשתמשים הרשומים. זוהי הטבלה היחידה שמשמשת ב-Authentication, ואליה מתייחסות כל הטבלאות האחרות באמצעות Username.
[IMAGE]
2. PlayerStats – טבלת סטטיסטיקות שחקן
מתעדכנת בסיום כל משחק. נוצרת רק לאחר שהמשתמש סיים את המשחק הראשון שלו (Upsert pattern – INSERT אם אינה קיימת, UPDATE אם כן).
[IMAGE]
3. MatchHistory – טבלת היסטוריית משחקים
בכל סיום משחק (גם רב-משתתפים וגם מול AI) נוסף רקורד חדש. זה מאפשר לכל שחקן לראות את היסטוריית המשחקים שלו.
[IMAGE]
4. Achievements – קטלוג ההישגים
טבלה סטטית שמכילה את כל ההישגים האפשריים. נוצרת פעם אחת ולא משתנה במהלך הפעלת המשחק.
[IMAGE]
5. PlayerAchievements – טבלת הקישור (Many-to-Many)
טבלת קישור המקשרת בין UserDataTable ל-Achievements. בכל הישג שהשחקן מרוויח, נוסף רקורד חדש. זוהי הטבלה היחידה שמייצגת קשר Many-to-Many.
[IMAGE]
6. LoginHistory – טבלת היסטוריית התחברויות
מתעדת כל ניסיון התחברות (מוצלח או כושל). מאפשרת לשחקן לראות אם מישהו ניסה להתחבר אליו, ולמנהל לאתר התנהגות חשודה.
[IMAGE]
7. RankedTierChanges – טבלת שינויי דרגה
מתעדת כל פעם שהשחקן עולה או יורד דרגה (Iron → Bronze, Bronze → Silver וכו׳). מאפשרת לעקוב אחרי ההיסטוריה התחרותית של השחקן.
[IMAGE]
## H2 ## 4.3 קשרי הגומלין (ERD)
הקשרים בין הטבלאות בנויים סביב Username כמזהה מרכזי, מאחר שהשם הוא ייחודי במערכת ומבטיח חיבור פשוט בין כל הנתונים של אותו משתמש:
UserDataTable ↔ PlayerStats – קשר 1-ל-1 דרך Username.
UserDataTable ↔ MatchHistory – קשר 1-ל-N (משתמש מופיע פעמיים, כ-Winner וכ-Loser).
UserDataTable ↔ LoginHistory – קשר 1-ל-N.
UserDataTable ↔ Achievements – קשר N-ל-M דרך טבלת הקישור PlayerAchievements.
UserDataTable ↔ RankedTierChanges – קשר 1-ל-N (כל עלייה/ירידה של דרגה היא רשומה נוספת).
MatchHistory ↔ RankedTierChanges – קשר 1-ל-1 (כל שינוי דרגה מקושר למשחק שגרם לו).
## H2 ## 4.4 דוגמאות לשאילתות במערכת
להלן דוגמאות לשאילתות אופייניות במערכת. כולן מוגנות מפני SQL Injection באמצעות פרמטרים (Placeholder ?).
שאילתת SELECT עם פרמטר (התחברות)
UserDB.GetByUsername — נקרא כל פעם שמשתמש מתחבר:
SELECT * FROM UserDataTable WHERE [Username] = ?
שאילתת INSERT עם 3 פרמטרים (רישום)
UserDB.AddToDB — נקרא בעת רישום משתמש חדש:
INSERT INTO UserDataTable (Username, PasswordHash, Gmail) VALUES (?, ?, ?)
שאילתת ORDER BY עם TOP (לוח מובילים)
StatsDB.GetLeaderboard — מחזירה את Top-50 מסודר לפי Elo, ושוברת שוויון לפי Wins:
SELECT TOP 50 Username, Wins, Losses, TotalGames, Elo
FROM PlayerStats
ORDER BY Elo DESC, Wins DESC
שאילתת COUNT לבדיקת קיום (לפני Upsert)
StatsDB.Upsert — בודקת אם השחקן כבר קיים ב-PlayerStats לפני שמחליטים האם להשתמש ב-INSERT או UPDATE:
SELECT COUNT(*) FROM PlayerStats WHERE Username = ?
שאילתת UPDATE עם מצברים (סיום משחק)
StatsDB.Upsert — מעלה את Wins ואת TotalGames בעבודה אחת:
UPDATE PlayerStats
SET [Wins] = [Wins] + 1, TotalGames = TotalGames + 1, Elo = ?
WHERE Username = ?
שאילתת SELECT מורכבת עם WHERE OR (היסטוריית משחקים)
HistoryDB.GetMatchHistory — מחזירה את כל המשחקים שבהם המשתמש הופיע, גם כמנצח וגם כמפסיד:
SELECT TOP 50 MatchId, WinnerUsername, LoserUsername, IsRanked,
       DatePlayed, WinnerEloDelta, LoserEloDelta,
       DurationSeconds, WinnerShots, WinnerHits
FROM MatchHistory
WHERE WinnerUsername = ? OR LoserUsername = ?
ORDER BY DatePlayed DESC
שאילתת INSERT עם 9 פרמטרים (תיעוד משחק)
HistoryDB.InsertMatch — בכל סיום משחק נכתבת רשומה מלאה ל-MatchHistory:
INSERT INTO MatchHistory
  (WinnerUsername, LoserUsername, IsRanked, DatePlayed,
   WinnerEloDelta, LoserEloDelta, DurationSeconds,
   WinnerShots, WinnerHits)
VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?)
שאילתת DELETE עם cascade ידני (מחיקת משתמש)
UserDB.DeleteUser — מנהל מוחק חשבון משתמש. נדרש למחוק גם רשומות תלויות:
DELETE FROM UserDataTable      WHERE Username = ?
DELETE FROM PlayerStats        WHERE Username = ?
DELETE FROM PlayerAchievements WHERE Username = ?
(MatchHistory ו-LoginHistory לא נמחקות – שומרים תיעוד היסטורי גם אחרי מחיקה.)

## H2 ## 5.3 תרשים פריסה (Deployment Diagram)
מבחינת פריסה (Deployment), המערכת רצה במספר צמתים:

שירות ngrok (בענן): מקבל את כל הבקשות מהאינטרנט הציבורי ומעביר אותן ל-localhost:5166 במחשב השרת. הדומיין הקבוע: https://retread-greeting-disburse.ngrok-free.dev
מחשבי לקוח (WPF Desktop): מותקנים על מחשבי המשתמשים. מתחברים ישירות לשרת ה-WCF דרך LAN.
דפדפנים (Blazor Web): רצים בכל מחשב/טלפון עם דפדפן מודרני. מתחברים לכתובת ngrok.
אפליקציות MAUI (Android): מותקנות על מכשיר אנדרואיד. מתחברות לכתובת ngrok דרך WiFi/Mobile data.
## H2 ## 5.4 זרימת הנתונים בין הרכיבים
נדגים את זרימת המידע באמצעות שני תרחישים מרכזיים:
תרחיש 1 – משחק רב-משתתפים בין שני שחקנים:
שחקן A מתחבר מ-WPF, שחקן B מתחבר מטלפון אנדרואיד (MAUI).
שניהם לוחצים PLAY ובוחרים Ranked.
MatchmakingService רואה ששניהם בתור (אחד דרך MultiplayerClient של Blazor, השני דרך SignalRGameClient של SignalR).
MatchmakingService יוצר MultiplayerGameSession חדש המכיל את שניהם דרך הממשק IGameClient.
שניהם מקבלים MatchFound notification ומעוברים להצבת ספינות.
בקרב, כל ירייה עוברת דרך GameSession.FireShot שמוודא תקינות, מעדכן את ה-state, שומר במסד הנתונים (בסיום), ומשגר ShotFired לשני השחקנים בו-זמנית.
תרחיש 2 – פתיחת לוח מובילים מ-MAUI:
המשתמש לוחץ "STATS" באפליקציית MAUI.
ApiClient.GetLeaderboardAsync שולח GET /api/stats/leaderboard?top=50 לכתובת ngrok.
ngrok מעביר את הבקשה ל-localhost:5166 במחשב השרת.
ASP.NET Core מנתב את הבקשה ל-StatsController.Leaderboard.
StatsDB.GetLeaderboard(50) מבצע שאילתת SELECT TOP 50 ORDER BY Elo ב-Access.
התוצאה מומרת ל-JSON ומוחזרת ל-MAUI שמציג אותה ב-CollectionView.
### H1 ### 6. צד שרת – שירותי WCF ו-Web
## H2 ## 6.1 שני שרתים – למה ולאיך
המערכת מכילה שני שרתים נפרדים, כל אחד עם תחום אחריות משלו:
שרת WCF (WcfServiceLibrary1) – משרת בעיקר את לקוח ה-WPF. מבוסס netTcpBinding לתקשורת דו-כיוונית מהירה ב-LAN, ועל basicHttpBinding לאימות וסטטיסטיקות. זהו השרת המקורי של הפרויקט.
שרת Web (BattleThunderWeb) – שרת ASP.NET Core שמתפקד בשלושה תפקידים: (1) Blazor Server המציג את אפליקציית ה-Web, (2) REST API ללקוח ה-MAUI, (3) SignalR Hub למשחק רב-משתתפים בין לקוחות Web ו-MAUI.
שני השרתים חולקים את אותו מסד נתונים (קובץ .accdb). זה מאפשר למשתמש להירשם דרך כל לקוח – ולהתחבר אחר-כך מכל לקוח אחר עם אותם פרטים.
## H2 ## 6.2 שירות WCF ראשי – IBattleshipService
ה-Contract של ה-WCF מוגדר בממשק IBattleshipService. הוא מציג את כל הפעולות שלקוח ה-WPF יכול לקרוא להן:
JoinGame(string username) – מצטרף לתור משחקים. אם יש יריב ממתין, נוצר GameSession חדש; אחרת השחקן ממתין.
PlaceShips(List&lt;ShipPlacementDto&gt; ships) – מציב את 5 הספינות של השחקן.
FireShot(int row, int col) – יורה בלוח של היריב, מחזיר AttackResultDto.
SendChatMessage(string text) – משדר הודעת צ׳אט ליריב.
RequestRematch() – מבקש משחק חדש מהיריב. אם שניהם הסכימו, המשחק מתחיל מחדש.
LeaveGame() – יוצא מהמשחק. השרת מודיע ליריב.
בנוסף, ה-Contract מכיל [CallbackContract(typeof(IBattleshipCallback))] שמאפשר לשרת לדחוף הודעות ללקוח, ללא צורך ב-Polling. הקריאות מהשרת אל הלקוח הן:
OnGameStarted, OnYourTurn, OnShotFired, OnChatReceived, OnGameOver, OnOpponentDisconnected, OnRematchRequested, OnRematchStarted ועוד.
## H2 ## 6.3 לוגיקה עסקית – GameSession ו-MultiplayerGameSession
ב-WCF, הלוגיקה של משחק יחיד נמצאת ב-GameSession.cs. ב-Web, היא נמצאת ב-MultiplayerGameSession.cs. שתי המחלקות עושות את אותו דבר עקרונית, אבל בארכיטקטורות שונות (WCF Callback Contract לעומת IGameClient interface).
ניהול state בזיכרון
כל משחק פעיל נשמר במילון בזיכרון של השרת (Dictionary&lt;int, GameSession&gt;). המפתח הוא מזהה המשחק. כך השרת מטפל בעשרות משחקים בו-זמנית מבלי לגעת במסד הנתונים בכל ירייה – רק בסיום משחק התוצאה נשמרת ב-DB.
Matchmaking
ב-MatchmakingService, יש שני תורים נפרדים: ranked ו-unranked. כשמישהו מצטרף, השרת בודק אם יש מישהו אחר בתור (עם שם משתמש שונה!), ואם כן – מתחיל משחק. אחרת השחקן מצטרף לתור עד שיריב נוסף יבוא.
סנכרון תורות עם נעילות
כל פעולת FireShot עטופה ב-lock(_lock) כדי שלא יתרחש מצב שבו שני שחקנים יורים בו-זמנית ושני הצדדים מנסים לעדכן את אותו state. הנעילה מוסרת לפני קריאת ה-Callback ליריב, כדי לא לגרום ל-Deadlock במקרה שה-Callback של היריב נכשל.
## H2 ## 6.4 תכנות אסינכרוני (Asynchronous Programming)
כל הפעולות החשובות במערכת אסינכרוניות. זה הכרחי כדי שה-UI לא יקפא בזמן שהשרת מחכה לתשובה.
בצד ה-WCF Client:
הלקוח עוטף כל קריאה לשרת ב-Task.Run, וכל אירוע Callback מהשרת עובר דרך Dispatcher.Invoke כדי להתעדכן ב-UI Thread.
public async Task<bool> FireShotAsync(int row, int col)
{
    return await Task.Run(() => _proxy.FireShot(row, col));
}
בצד ה-Web (Blazor):
כל ה-Razor components משתמשים ב-async event handlers. הקריאות לשרת מועברות דרך MultiplayerClient שעוטף אותן ב-await. כאשר הסטטוס משתנה (StateChanged event), נקרא InvokeAsync(StateHasChanged) כדי לעדכן את ה-UI ב-thread הנכון.
בצד ה-MAUI:
ApiClient עוטף את HttpClient ומחזיר Task&lt;T?&gt; לכל קריאה. MultiplayerClient משתמש ב-Microsoft.AspNetCore.SignalR.Client ובכל אירוע מ-Hub משתמש ב-MainThread.BeginInvokeOnMainThread כדי להבטיח שעדכוני UI יבוצעו על ה-UI Thread.
## H2 ## 6.5 שכבת גישת הנתונים (Data Access Layer)
שכבת ה-DB מורכבת ממחלקה אבסטרקטית BaseDB וממחלקות יורשות UserDB, StatsDB ו-HistoryDB. הירושה מאפשרת שיתוף קוד (פעולות SELECT/INSERT/UPDATE/DELETE גנריות) ובאותה עת לאפשר לכל יורשת לממש את ה-CreateModel שלה (איך להמיר רשומה ב-DB לאובייקט מודל).
מחלקת BaseDB
המחלקה האבסטרקטית BaseDB מספקת:
connectionString סטטי – שמירת ה-Connection String פעם אחת לכל המופעים.
connection, command, reader – אובייקטים של OleDb שמשותפים לכל הפעולות.
NewEntity() אבסטרקטית – כל יורשת מחזירה את סוג ה-Entity שלה (User, וכו׳).
CreateModel(Base entity) וירטואלית – כל יורשת ממירה רשומה ב-reader לאובייקט בזיכרון.
Select(string sql) – פעולת SELECT גנרית שמחזירה List&lt;Base&gt; באמצעות פולימורפיזם.
SaveChanges(OleDbCommand cmd, Base entity) – פעולה גנרית ל-INSERT/UPDATE/DELETE.
Count, Max, InsertAndGetID – פעולות עזר נוספות.
המחלקות היורשות
UserDB יורשת מ-BaseDB ומוסיפה:
GetByUsername(string) – שליפת משתמש לפי שם (להתחברות).
GetById(int) – שליפה לפי מזהה.
GetAllUsers() – שליפת כל המשתמשים (לדף Admin).
DeleteUser(string) – מחיקת משתמש עם cascade ידני ל-PlayerStats ול-PlayerAchievements.
StatsDB מוסיפה: GetStats, GetLeaderboard, SaveResult, SaveRankedResult, ResetStats, GetEloAfter, Upsert.
HistoryDB מוסיפה: InsertMatch, GetMatchHistory, GetAllMatches, CountWinsByMode, CountTotalMatches, InsertTierChange, GetAchievements, TryAwardAchievement, InsertLogin, GetLoginHistory, EvaluateAchievementsForMatch.
## H2 ## 6.6 REST API – ב-ASP.NET Core
הוספתי שכבת REST API לשרת ה-Web כדי שלקוח ה-MAUI יוכל לפנות אליו. ה-API מארגן ב-Controllers לפי תחום:
האימות מתבצע באמצעות Bearer Token. ה-TokenService הוא Singleton שמייצר ושומר Tokens אטומים (32 בייטים אקראיים → base64). בכל קריאה מוגנת, ה-ApiAuthAttribute filter מאמת את ה-Token, מוצא את ה-Username, ומשים אותו ב-HttpContext.Items כך שה-Controller יוכל לגשת אליו.
## H2 ## 6.7 SignalR Hub – BattleshipHub
ה-Hub חושף את אותן פעולות שיש ב-WCF (JoinQueue, PlaceShips, FireShot, SendChat, Surrender, UnplaceShips) אבל דרך WebSocket. בכניסת הלקוח (OnConnectedAsync), ה-Hub:
מקרא את ה-Token מתוך query string (?token=...).
מאמת אותו דרך TokenService.TryResolve.
אם תקין – יוצר SignalRGameClient ושומר אותו ב-SignalRClientRegistry.
אם לא תקין – Context.Abort() לסגירה מיידית.
כל פעולה שהלקוח קורא לה (FireShot למשל) מועברת ל-SignalRGameClient שמטפל בה. הוא ממומש את הממשק IGameClient – אותו ממשק שה-MultiplayerClient של Blazor ממומש – ולכן MatchmakingService ו-MultiplayerGameSession עובדים עם שניהם בלי לדעת מה ההבדל ביניהם. זוהי דוגמה מצוינת לפולימורפיזם בפעולה.

### H1 ### 8. אבטחה והגנה על נתונים
## H2 ## 8.1 הצפנת סיסמאות עם BCrypt
סיסמאות הן הנתון הכי רגיש במערכת. אסור לאחסן אותן בטקסט פתוח, ואסור גם להצפין אותן באלגוריתם הפיך (כמו AES) – כי אם אבטחת המסד נפרצת, מישהו יכול לפענח אותן בחזרה.
הפתרון הנכון הוא Hash חד-כיווני – פונקציה שלא ניתן להפוך. השתמשתי ב-BCrypt דרך הספרייה BCrypt.Net-Next, שעוטפת את כל הפרטים:
public static class PasswordManager
{
    public static string Hash(string password) =>
        BCrypt.Net.BCrypt.HashPassword(password);
    public static bool Verify(string password, string hash) =>
        BCrypt.Net.BCrypt.Verify(password, hash);
}
BCrypt מוסיף Salt אקראי לכל סיסמה (16 בייטים) ומבצע 10 סבבי איטרציה כברירת מחדל. זה אומר שחישוב Hash של סיסמה אחת לוקח כ-100ms – מה שמקשה על ניסיונות Brute Force אבל לא משפיע על תהליך התחברות אמיתי.
בעת התחברות, BCrypt.Verify משווה את הסיסמה ל-Hash בזמן קבוע (Constant-Time Comparison), מה שמונע Timing Attacks – ניסיון לנחש סיסמה לפי הזמן שלוקח לאמת אותה.
## H2 ## 8.2 הגנה מ-SQL Injection
SQL Injection הוא אחד התקיפות הנפוצות ביותר על מסדי נתונים. הוא קורה כשמכניסים קלט משתמש ישירות לתוך מחרוזת SQL, ומשתמש זדוני יכול להזריק תקנים כמו ' OR '1'='1 שמשנים את משמעות השאילתה.
ההגנה היחידה האמיתית היא להשתמש בפרמטרים (Parameterized Queries). כל שאילתה במערכת משתמשת ב-OleDbParameter עם Placeholder ?:
// נכון - מוגן מ-SQL Injection:
string sql = "SELECT * FROM UserDataTable WHERE [Username] = ?";
command.Parameters.AddWithValue("?", username);
// שגוי - פגיע ל-SQL Injection:
// string sql = $"SELECT * FROM UserDataTable WHERE Username = '{username}'";
OleDb מנקה את הערך אוטומטית: אם המשתמש מזין ' OR '1'='1, ה-Driver עוטף אותו במרכאות ומבריח את התווים המיוחדים. הוא יתחפש ל-Username ולא לתחביר SQL.
שאילתות שלוקחות int (כמו GetLeaderboard עם TOP {topN}) מוגנות גם הן – אבל מסיבה אחרת: int נבדק ע"י .NET לפני שמגיע ל-SQL, ולא ניתן לעבור עליו string.
## H2 ## 8.3 ניהול Tokens אטומים
ב-API ה-REST של ה-Web, אימות מתבצע באמצעות Bearer Token. הטוקן הוא מחרוזת אטומה (Opaque) של 32 בייטים אקראיים שנוצרים ע"י RandomNumberGenerator.Fill:
public string Issue(string username)
{
    Span<byte> buf = stackalloc byte[32];
    RandomNumberGenerator.Fill(buf);
    string token = Convert.ToBase64String(buf)
        .Replace('+', '-').Replace('/', '_').TrimEnd('=');
    _byToken[token] = new Entry(username, DateTime.UtcNow + SlidingExpiry);
    return token;
}
32 בייטים = 256 ביט אקראיים. ניחוש טוקן תקף שווה לאיתור מחט בערימת חציר בגודל יקום. תוקף הטוקן הוא 24 שעות מהקריאה האחרונה (Sliding Expiry), מה שאומר שמשתמש פעיל לא יוצא מהמערכת באמצע השימוש.
## H2 ## 8.4 אימות ב-SignalR Hub
ב-SignalR, האימות מתבצע בכניסת הלקוח (OnConnectedAsync). הטוקן מועבר ב-query string (?token=...) של ה-WebSocket URL. אם הטוקן אינו תקין, ה-Hub קורא ל-Context.Abort() ומפסיק את ההתחברות מיד.
## H2 ## 8.5 הגנת Admin
פאנל ה-Admin מוגן בשתי שכבות:
בצד הלקוח (Razor) – הדף בודק ב-OnInitialized אם Auth.Username הוא Admin. אם לא, מבצע redirect ל-/play.
בצד השרת – אין ערך לטריגרים ב-UI אם המנהל יכול לעקוף אותם דרך URL ישיר. לכן, פעולות הניהול (DeleteUser, ResetStats) פתוחות לכל המשתמשים המאומתים – אבל הן רק נקראות מתוך הדף /admin שמוגן. אם בעתיד נרצה לחזק, ניתן להוסיף בדיקה גם ב-Controller.
### H1 ### 9. תהליכים מרכזיים במערכת
## H2 ## 9.1 תהליך התחברות
התחברות היא התהליך הראשון שכל משתמש עובר. השלבים:
המשתמש מזין Username + Password ב-LoginPage.
הלקוח שולח את הפרטים לשרת (WCF, REST או SignalR).
השרת קורא ל-UserDB.GetByUsername(username), שמבצע SELECT עם פרמטר.
אם המשתמש קיים, השרת קורא ל-PasswordManager.Verify(password, user.PasswordHash) שמשתמש ב-BCrypt.
אם הסיסמה תקינה, השרת:
        ▸ ב-WCF – שומר את שם המשתמש ב-Session ומחזיר LoginResult.Success = true.
        ▸ ב-REST – מייצר Token חדש ב-TokenService ומחזיר אותו ב-AuthResponse.
בכל מקרה, HistoryDB.InsertLogin(username, wasSuccessful) מתעד את הניסיון.
הלקוח שומר את ה-Token (אם יש), ועובר לתפריט הראשי.
## H2 ## 9.2 תהליך התאמת משחק (Matchmaking)
בלחיצה על PLAY, ה-MatchmakingService מנהל את התור:
הלקוח קורא ל-JoinQueue(ranked: true/false).
MatchmakingService בודק אם יש כבר מישהו בתור (עם שם שונה!).
אם כן – שני השחקנים מוצאים מהתור, נוצר MultiplayerGameSession חדש, ושני הצדדים מקבלים MatchFound notification.
אם לא – השחקן מצטרף לתור ומקבל QueueState notification (שמראה שהוא ממתין).
עד שיריב יבוא, השחקן יכול ללחוץ CANCEL SEARCH בכל רגע. זה קורא ל-LeaveQueue ומסיר אותו.
## H2 ## 9.3 תהליך הצבת ספינות
לאחר Match Found, שני השחקנים מועברים ל-ShipPlacementPage:
כל אחד מציב 5 ספינות (Carrier, Battleship, Submarine, 2× Destroyer).
בלחיצה על READY FOR BATTLE, הלקוח קורא ל-PlaceShips(ships) עם הרשימה.
השרת שומר את המיקומים בצד שלו.
אם רק אחד מהשניים סיים – השני מקבל OpponentReady notification, והשרת ממתין.
כאשר שני הצדדים מציבו ספינות, השרת מגריל מי מתחיל (Random) ושולח GameStarted לשניהם.
שני הצדדים מועברים ל-GamePage / AiGamePage / MultiplayerGamePage.
## H2 ## 9.4 תהליך ירייה
הירייה היא הפעולה המרכזית במשחק. כאשר השחקן בוחר תא ולוחץ FIRE:
הלקוח קורא ל-FireShot(row, col).
השרת מוודא שזה התור הנכון של הלקוח.
בודק אם בתא יש ספינה (לפי PlayerShips של היריב שנשמר בצד השרת).
אם פגיעה – בודק אם זאת הפגיעה האחרונה של אותה ספינה (כלומר ספינה הוטבעה).
אם הוטבעה – בודק אם כל הספינות של היריב הוטבעו (סוף המשחק).
בונה AttackResultDto עם Row, Col, IsHit, IsSunk, SunkShipType, IsGameOver.
שולח ShotFired notification לשני השחקנים בו-זמנית.
מחליף את התור (פסיכולוגית – אצלנו אין hit-then-shoot-again כי זה הופך משחק לאינסופי).
שולח YourTurn notification ליריב.
אם זה היה משחק מנצח, כותב את התוצאה ל-DB דרך HistoryDB.InsertMatch ו-StatsDB.SaveRankedResult/SaveResult, ושולח GameOver לשניהם עם המידע.
## H2 ## 9.5 אלגוריתם ה-AI
ה-AI שתי שכבות עבודה: Hunt Mode ו-Target Mode.
Hunt Mode (חיפוש)
ברגע שלא יודעים איפה ספינה, ה-AI עובר למצב חיפוש. במקום לירות אקראית או בתבנית קבועה, הוא משתמש ב-Probability Density:
לכל תא בלוח, ה-AI מחשב כמה דרכים שונות יש להציב את כל הספינות שעדיין חיות, כך שאחת מהן עוברת דרך התא.
התא עם הציון הגבוה ביותר נבחר לירייה.
טבעי שמרכז הלוח מקבל ציון גבוה יותר, כי יותר הצבות עוברות דרכו.
Target Mode (מעקב)
ברגע שיש פגיעה (Hit) ראשונה, ה-AI עובר למצב מעקב:
הוא מוסיף את התא ל-Unresolved Hits.
בירייה הבאה, הוא נותן ציון גבוה ל-4 התאים הסמוכים לפגיעה.
אם פגע שוב, יש לו שני תאים סמוכים – הוא מזהה את הציר (אופקי או אנכי) וממשיך באותו ציר.
בכל פגיעה הוא בודק האם הספינה הוטבעה. אם כן, הוא מוסיף את 8 התאים סביב הספינה ל-No-Ship Zone (כי הכללים אומרים שספינות לא נוגעות זו בזו).
## H2 ## 9.6 תהליך הניתוק
ניתוק יכול לקרות בשלושה אופנים:
ניתוק יזום (LeaveGame) – המשתמש לוחץ Surrender. הצד השני מקבל הודעת ניצחון. נשמר ב-DB.
סגירת חלון – ב-WPF, מתבצע WindowClosing event שקורא ל-LeaveGame לפני סגירה.
ניתוק רשת או קריסה – ב-WCF, אירוע channel.Faulted/Closed מתפוצץ. ב-SignalR, OnDisconnectedAsync. השרת מנקה את ה-Session ושולח OnOpponentDisconnected ליריב.

## H2 ## 14.2 דוגמת קוד – מחלקת BaseDB (מחלקה אבסטרקטית)
מחלקה זו היא הבסיס לכל הגישה למסד הנתונים. היא מדגימה את עיקרון ה-DRY (Don't Repeat Yourself) ואת השימוש בפולימורפיזם:
public class BaseDB
{
    private static string connectionString = null;
    protected OleDbConnection connection;
    protected OleDbCommand command;
    protected OleDbDataReader reader;
    public BaseDB()
    {
        if (connectionString == null)
        {
            string baseFolder = AppDomain.CurrentDomain.BaseDirectory;
            connectionString = @"Provider=Microsoft.ACE.OLEDB.12.0;Data Source="
                + baseFolder + "...ShipDataBaseaccdb.accdb;Persist Security Info=True";
        }
        connection = new OleDbConnection(connectionString);
        command = new OleDbCommand { Connection = connection };
    }
    protected virtual Base NewEntity() => null;
    protected virtual Base CreateModel(Base entity)
    {
        if (entity != null) entity.Id = (int)reader["ID"];
        return entity;
    }
    protected virtual List<Base> Select(string sql)
    {
        List<Base> list = new List<Base>();
        command.CommandText = sql;
        try
        {
            connection.Open();
            reader = command.ExecuteReader();
            while (reader.Read())
                list.Add(CreateModel(NewEntity()));
        }
        finally
        {
            reader?.Close();
            if (connection.State == ConnectionState.Open) connection.Close();
        }
        return list;
    }
}
## H2 ## 14.3 דוגמת קוד – אלגוריתם ה-AI
המתודה ChooseHuntTarget מהמחלקה WebAIOpponent. היא מחשבת Probability Density ובוחרת את התא עם הציון הגבוה ביותר:
private (int r, int c) ChooseHuntTarget()
{
    var density = new int[10, 10];
    foreach (int size in _aliveShipSizes)
    {
        // הצבות אופקיות
        for (int r = 0; r < 10; r++)
        for (int c = 0; c <= 10 - size; c++)
            if (CanPlaceLine(r, c, size, horizontal: true))
                for (int i = 0; i < size; i++) density[r, c + i]++;
        // הצבות אנכיות
        for (int r = 0; r <= 10 - size; r++)
        for (int c = 0; c < 10; c++)
            if (CanPlaceLine(r, c, size, horizontal: false))
                for (int i = 0; i < size; i++) density[r + i, c]++;
    }
    int maxDensity = 0;
    var best = new List<(int, int)>();
    for (int r = 0; r < 10; r++)
    for (int c = 0; c < 10; c++)
    {
        if (_firedAt.Contains((r, c))) continue;
        if (_noShipZone.Contains((r, c))) continue;
        int s = density[r, c];
        if (s > maxDensity) { maxDensity = s; best.Clear(); best.Add((r, c)); }
        else if (s == maxDensity) best.Add((r, c));
    }
    return best[_rng.Next(best.Count)];
}
## H2 ## 14.4 דוגמת קוד – Hub של SignalR
מתודת OnConnectedAsync של BattleshipHub שמאמתת את הלקוח לפי טוקן:
public override async Task OnConnectedAsync()
{
    string token = Context.GetHttpContext()?.Request.Query["token"].ToString();
    string username = _tokens.TryResolve(token);
    if (string.IsNullOrEmpty(username))
    {
        Context.Abort();  // דחיית התחברות אנונימית
        return;
    }
    var client = new SignalRGameClient(_hubContext, Context.ConnectionId,
                                       username, _matchmaking);
    _registry.Register(Context.ConnectionId, client);
    await base.OnConnectedAsync();
}
