# =================== פרק 1 ===================
=1 1. מבוא ורקע לפרויקט

=2 1.1 רקע והשראה לפרויקט
. הבחירה לפתח את Online Checkers נובעת מאהבה אישית למשחקי לוח אסטרטגיים, ובמיוחד למשחק הדמקה הקלאסי. הכללים פשוטים ללמידה, אך מתחתם מסתתר עומק טקטי אמיתי: כל מהלך משפיע על מבנה הלוח, אכילה כפויה משנה את מאזן הכוחות, והכתרת מלך הופכת כלי פשוט לעוצמתי. השילוב הזה יוצר חוויה הוגנת ולא צפויה גם אחרי משחקים רבים.
. המטרה שלי בפרויקט הייתה לקחת את החוויה הקלאסית הזו ולהעביר אותה לעידן המודרני: לאפשר משחק רב-משתתפים בזמן אמת דרך הרשת בין שני שחקנים היושבים על מחשבים שונים, להוסיף יריב מבוסס מחשב לשחקן הבודד, לנהל מערכת דירוג Elo גלובלית, ולספק את כל זה דרך שלושה לקוחות נפרדים: דסקטופ (WPF), אתר ניהול בדפדפן (ASP.NET), ומובייל (MAUI), שכולם פונים לאותו שרת ולאותו מסד נתונים.
. המערכת בנויה כארכיטקטורת שרת-לקוח מלאה: השרת אחראי על הלוגיקה, על שמירת הנתונים ועל סנכרון השחקנים, והלקוחות בכל שלוש הפלטפורמות הם תצוגה ובקרת מצב בלבד. גישה זו מבטיחה שכל חוקי המשחק נאכפים במקום אחד מרכזי ומאובטח.

=2 1.2 שם הפרויקט ותיאורו
. שם הפרויקט: Online Checkers, משחק דמקה רב-משתתפים בזמן אמת.
. המערכת היא יישום שרת-לקוח מלא. כל שחקן נרשם, מתחבר ומתחיל קרב תורות על לוח 8x8 מול יריב אנושי או מול יריב מבוסס מחשב (בוט). הכלים ניצבים במצב פתיחה קבוע, וכל תור השחקן בוחר כלי ומבצע מהלך חוקי: תנועה אלכסונית פשוטה או אכילה. במהלך המשחק כל מהלך מתעדכן בזמן אמת אצל שני הצדדים, מתעדכן מצב הלוח, נשמרת היסטוריית המהלכים, ומתבצעות הצעת תיקו והתפטרות. בסיום נשמרות הסטטיסטיקות במסד הנתונים, מתעדכן דירוג ה-Elo, וניתן לצפות שוב במשחק שהסתיים. בנוסף קיים ממשק ניהול (Admin) לחסימת משתמשים ולצפייה בנתוני המערכת.

=2 1.3 קהל היעד
. המערכת פונה לכמה סוגי משתמשים שונים:
. שחקנים פרטיים שאוהבים משחקי לוח אסטרטגיים, מכל גיל, ללא צורך בידע טכני.
. שחקנים שמחפשים חוויה מהירה מול יריב חי, ישירות מהמחשב, הדפדפן או הטלפון.
. שחקנים בודדים שרוצים לתרגל מול יריב ממוחשב מבלי להמתין ליריב אנושי.
. שחקנים תחרותיים המעוניינים לטפס בטבלת המובילים הגלובלית באמצעות מערכת דירוג Elo.
. מנהלי מערכת (Admin) האחראים על ניהול הקהילה, חסימת משתמשים ומעקב אחר נתוני השרת.

=2 1.4 מטרות המערכת
. מטרות על:
. יצירת חוויית משחק רב-משתתפים בזמן אמת מול שרת מרכזי אחד.
. אכיפת כל חוקי הדמקה בצד השרת בלבד, כך שאף שחקן אינו יכול לרמות.
. הצגת אותה מערכת באמצעות שלושה לקוחות שונים (WPF, אתר ניהול ו-MAUI) המתחברים לאותו שרת ולאותו מסד נתונים.
. מתן ממשק נקי, אחיד וברור בכל שלוש הפלטפורמות.
. מערכת דירוג Elo גלובלית לדירוג השחקנים לפי תוצאותיהם.
. מטרות נלוות:
. הצפנת סיסמאות באמצעות PBKDF2 עם Salt אקראי למניעת דליפות מידע.
. זיהוי אוטומטי של ניתוקי לקוח (קריסה או ניתוק רשת) ושחרור היריב מהמשחק.
. יריב ממוחשב (בוט) לשחקן הבודד.
. צפייה חוזרת (Replay) במשחקים שהסתיימו, מהלך אחר מהלך.
. פאנל ניהול (Admin) המאפשר לצפות בכל המשתמשים, לחסום משתמשים ולראות נתוני שרת.

=2 1.5 תיאור כללי של המערכת
. המערכת בנויה לפי ארכיטקטורת שכבות נקייה, עם הפרדה מלאה בין שכבת התצוגה, שכבת הלוגיקה ושכבת הנתונים. בחירה זו מאפשרת לצרף לקוחות נוספים בעתיד מבלי לגעת בקוד השרת או במסד הנתונים, וכך אכן נוספו אתר הניהול ואפליקציית המובייל לאחר שכבר היה לקוח WPF פעיל.
. השכבות העיקריות במערכת הן:
. שכבת Model: מחלקות נתונים (User, Board, Piece, Square, Move, GameStateDto ועוד) המשותפות לשרת וללקוחות דרך WCF DataContract.
. שכבת ViewDB: שכבת גישה למסד הנתונים, היורשת ממחלקה אבסטרקטית BaseDB המכילה את הפעולות הכלליות (Select, SaveChanges) עם הגנה מלאה מפני SQL Injection באמצעות פרמטרי OleDb.
. שכבת BusinessLogic: לוגיקה עסקית, הכוללת את מנוע המשחק (CheckersEngine), ניהול המשחקים (GameManager), היריב הממוחשב (BotEngine), אימות (AuthService) והצפנת סיסמאות (PasswordHasher).
. שכבת WCF Server: שירות WCF המתארח כתהליך עצמאי וחושף שתי נקודות קצה במקביל (net.tcp ו-basicHttp).
. שכבת לקוח WPF: ממשק שולחני עשיר, מבוסס Views ו-ViewModels בתבנית MVVM, עם ניווט בין מסכים ועדכון מצב המשחק בזמן אמת.
. שכבת אתר הניהול (ASP.NET Razor Pages): אתר בדפדפן המספק למנהל לוח בקרה, ניהול משתמשים וצפייה במשחקים אחרונים.
. שכבת לקוח MAUI: אפליקציה נטיבית לאנדרואיד ול-Windows, המתחברת לאותו שירות.

=2 1.6 גבולות המערכת
. בכל פרויקט תוכנה חשוב להגדיר במפורש מה כלול ומה אינו כלול, כדי לא לקרוס תחת עומס דרישות. הבחירות שלי היו:
. המערכת כוללת:
. שלושה לקוחות פעילים: WPF Desktop, אתר ניהול בדפדפן, ו-MAUI (Android ו-Windows).
. שני סוגי משתמשים, שחקן רגיל ומנהל (Admin), כאשר ההבחנה נשמרת בשדה Role בטבלת המשתמשים.
. משחק מול יריב ממוחשב ומול שחקן אחר.
. אכיפת כל חוקי הדמקה בצד השרת, כולל אכילה כפויה, שרשור אכילות והכתרת מלך.
. המערכת אינה כוללת:
. הצפנת תקשורת ברמת התווך (TLS/HTTPS); הקריאות מתבצעות ב-net.tcp ו-HTTP בסביבה מקומית. הצפנה ניתנת להוספה בעתיד דרך הגדרת תעודה.
. אינטגרציה עם רשתות חברתיות או התחברות דרך שירות חיצוני.
. יריב ממוחשב מבוסס אלגוריתם חיפוש מתקדם; הבוט הנוכחי בוחר מהלך חוקי בלבד, עם העדפה להכתרה.

=2 1.7 סביבות פיתוח, שפות ושכבות
. סביבת פיתוח: Microsoft Visual Studio.
. שפות תכנות: C# עבור לוגיקת השרת והלקוחות, XAML עבור עיצוב ממשק המשתמש בדסקטופ ובמובייל, ו-HTML ו-Razor עבור אתר הניהול.
. טכנולוגיות מרכזיות:
. WPF (Windows Presentation Foundation) לצד הלקוח השולחני.
. WCF (Windows Communication Foundation) לניהול התקשורת מול השרת המרכזי.
. ASP.NET Core Razor Pages לאתר הניהול.
. NET MAUI. לאפליקציית המובייל החוצה-פלטפורמות.
. OleDb לעבודה מול בסיס נתונים Microsoft Access.
. ארכיטקטורת שכבות: הפרויקט מחולק לשכבות Model (ייצוג הנתונים), ViewDB (גישה למסד הנתונים), BusinessLogic (לוגיקת המשחק והדירוג) והשירות (CheckersService).

=2 1.8 אתגרים מרכזיים בפרויקט
. במהלך הפיתוח התמודדתי עם כמה אתגרים מרכזיים. אני מציין כאן את החשובים שבהם, יחד עם הפתרון שמצאתי לכל אחד:
. סנכרון מצב המשחק בין שני שחקנים: הצורך לוודא ששני הצדדים רואים תמיד את אותו מצב לוח, ושמהלך של אחד לא יידרס על-ידי מצב ישן של השני. הפתרון: השרת מחזיק עותק יחיד ואמין של מצב המשחק בזיכרון, וכל הלקוחות דוגמים אותו במרווחים קצרים. מהלך מאושר רק לאחר שעבר בדיקת חוקיות בשרת.
. חישוב כל רצפי האכילה: על פי חוקי הדמקה, אכילה היא חובה, ויש להמשיך ולאכול ברצף כל עוד אפשר. הפתרון: מימוש חיפוש לעומק (DFS) רקורסיבי במנוע המשחק, המסיר את הכלי שנאכל בכל שלב וממשיך לחפש אכילות נוספות עד שלא נותרות אפשרויות.
. זיהוי ניתוקי לקוח: לקוח שקורס אינו מספיק להודיע לשרת שעזב, ולכן היריב עלול להישאר תקוע. הפתרון: טיימר בשרת (StaleSweep) הסורק את המשחקים הפעילים ומסיים משחק שבו שחקן לא דיווח על פעילות במשך פרק זמן מוגדר, תוך עדכון התוצאה והטלת קנס דירוג.

=2 1.9 חידושים ומאפיינים מיוחדים
. יש בפרויקט כמה מאפיינים שאינם נפוצים בפרויקטי תיכון:
. אכיפת כל חוקי המשחק בצד השרת בלבד (Anti-Cheat): הלקוח אינו יכול לזייף אכילה, לדלג על אכילת חובה או לבצע מהלך לא חוקי.
. שלושה לקוחות נפרדים (WPF, אתר ניהול ו-MAUI) המתחברים לאותו שרת ולאותו מסד נתונים דרך חוזה DataContract משותף.
. מנוע משחק מלא המטפל בשרשור אכילות באמצעות חיפוש רקורסיבי לעומק.
. מערכת דירוג Elo המתעדכנת אוטומטית בסיום כל משחק, עם רצפה שמונעת צניחת דירוג לאפס.
. צפייה חוזרת (Replay) במשחקים שהסתיימו, המבוססת על שמירת מצב הלוח לאחר כל מהלך.
. זיהוי אוטומטי של ניתוקים באמצעות טיימר ניקוי בשרת.
. הצפנת סיסמאות חזקה באמצעות PBKDF2-SHA256 עם Salt אקראי והשוואה בזמן קבוע.

# =================== פרק 2 ===================
=1 2. מענה למחוון על פי דרישות הבחינה
. פרק זה מציג את המענה לדרישות המחוון של חלופת "שירותי אינטרנט, תכנות אסינכרוני ומסדי נתונים". המענה מוצג בשקיפות מלאה: לכל סעיף כתוב מה הפרויקט מספק, ובמקום שבו המענה חלקי הדבר מצוין במפורש.

=2 2.1 דרישות חובה (סעיפים 1 עד 8)
. מסד נתונים מנורמל: המערכת משתמשת ב-Microsoft Access עם שלוש טבלאות (Users, Games, Moves), הכוללות מפתחות ראשיים ומפתחות זרים.
. פעולות CRUD מלאות: המערכת מבצעת INSERT (רישום משתמש, שמירת משחק ומהלך), SELECT (התחברות, טבלת מובילים, היסטוריה), UPDATE (עדכון סטטיסטיקות ודירוג) ו-DELETE (מחיקת משתמש בידי מנהל).
. שאילתות מאובטחות: כל השאילתות משתמשות בפרמטרים של OleDb להגנה מפני SQL Injection.
. ארכיטקטורת שרת-לקוח: שרת WCF מרכזי המשרת שלושה לקוחות נפרדים.
. ממשק משתמש גרפי: ממשקים בנויים ב-WPF, ב-Razor וב-MAUI.
. ניהול משתמשים והרשאות: רישום, התחברות, והפרדה בין שחקן רגיל למנהל.

=2 2.2 הרחבות לסעיף 9 (יכולות בסיס)
. ירושה ופולימורפיזם: כל מחלקות הנתונים יורשות ממחלקת הבסיס Base, וכל מחלקות הגישה לנתונים יורשות מ-BaseDB ומממשות פעולות מופשטות בדרכן.
. אירועים ו-Delegates: לקוח ה-WPF משתמש באירועים מותאמים (RoutedEvent) ובפקודות (RelayCommand) לקישור בין הממשק ללוגיקה.
. הצפנה: סיסמאות המשתמשים מוצפנות באמצעות PBKDF2-SHA256.

=2 2.3 הרחבות לסעיף 10 (יכולות מתקדמות)
. תכנות אסינכרוני: שכבת הגישה לנתונים והקריאות לשרת מבוצעות באופן אסינכרוני (Async/Await) כדי שהממשק לא ייתקע.
. הגנה מפני SQL Injection: כל שאילתה מבוצעת עם פרמטרים בלבד.
. אכיפת לוגיקה בצד השרת: כל חוקי המשחק מחושבים ונאכפים בשרת, מה שמונע מהלכים לא חוקיים מצד הלקוח.

=2 2.4 סיכום המענה למחוון
. שמונה דרישות החובה מקבלות מענה מלא, ובנוסף נוספו הרחבות בסעיף 9 (ירושה, אירועים, הצפנה) ובסעיף 10 (אסינכרוניות, הגנה מפני SQL Injection, אכיפת חוקים בצד השרת). החוזק היחסי של הפרויקט מתבטא בכך שאותו שרת משרת שלושה לקוחות שונים, ובכך שכל חוקי המשחק נאכפים אך ורק בשרת.

# =================== פרק 3 ===================
=1 3. ניתוח המערכת

=2 3.1 מסמך ייזום
. שם הפרויקט: Online Checkers, משחק דמקה רב-משתתפים.
. בעיה קיימת: משחק הדמקה הקלאסי מצריך שני אנשים היושבים פיזית באותו מקום ולוח אחד. אין דרך נוחה לשחק נגד חבר שגר רחוק, ואין מעקב אחר היסטוריית המשחקים, הדירוג או הסטטיסטיקות של השחקן.
. פתרון מוצע: מערכת שרת-לקוח המאפשרת לשני שחקנים לשחק דמקה בזמן אמת מכל מקום, עם יריב ממוחשב לשחקן הבודד, מערכת רישום והתחברות מאובטחת, סטטיסטיקות אישיות, טבלת מובילים גלובלית, צפייה חוזרת במשחקים, ניהול ניתוקים אוטומטי, ולקוחות לכמה פלטפורמות.
. ערך עסקי:
. משחק רב-משתתפים מהיר וממוקד מכל מכשיר.
. יריב ממוחשב שמאפשר תרגול גם ללא יריב אנושי.
. שקיפות סטטיסטית: כל שחקן יודע כמה ניצח, כמה הפסיד ומה דירוגו.
. תחרותיות גלובלית באמצעות טבלת המובילים.
. גמישות פלטפורמה: משחק מהמחשב (WPF), מהדפדפן או מהטלפון (MAUI).

=2 3.2 מצב קיים מול מצב עתידי
. מצב קיים: משחק דמקה פיזי או יישומים מקומיים בלבד, ללא ניהול משתמשים, ללא דירוג וללא שמירת היסטוריה.
. מצב עתידי (המערכת שלי): מערכת מקוונת מלאה עם חשבונות משתמש, דירוג Elo, היסטוריית משחקים, צפייה חוזרת, יריב ממוחשב, ניהול מנהלים, ושלושה לקוחות מעל שרת מרכזי אחד.

=2 3.3 בעלי תפקידים במערכת
. שחקן אורח: יכול לשחק מול הבוט ללא הרשמה.
. שחקן רשום: נרשם, מתחבר, משחק מול שחקנים אחרים ומשפיע על דירוגו, וצופה בהיסטוריה ובטבלת המובילים.
. מנהל (Admin): כל יכולות השחקן הרשום, ובנוסף צפייה בכל המשתמשים, חסימת משתמשים וצפייה בנתוני השרת.
. השרת: שחקן לוגי שמנהל את כל המשחקים, אוכף את החוקים ושומר את הנתונים.

=2 3.5 עץ תהליכים (Process Tree)
. עץ התהליכים מתאר את האפשרויות שיש לשחקן בכל רגע, לפי מצב המערכת. מהשורש (Online Checkers) מתפצלים כמה ענפים עיקריים:
. שורש: Online Checkers.
. ענף אימות וזיהוי: רישום משתמש חדש, התחברות, יציאה.
. ענף משחק מול הבוט: התחלת משחק, ביצוע מהלכים, סיום, חזרה ללובי.
. ענף משחק רב-משתתפים: כניסה לתור התאמה, המתנה ליריב, משחק, סיום, חזרה ללובי.
. ענף צפייה בנתונים: טבלת מובילים, היסטוריית משחקים, צפייה חוזרת, פרופיל.
. ענף ניהול (Admin בלבד): רשימת משתמשים, חסימת משתמש, צפייה בנתוני השרת.

. Games ו-Moves: קשר 1 ל-N. לכל משחק שייכים מהלכים רבים, וכל מהלך שייך למשחק אחד.

=1 4. בסיס הנתונים

=2 4.1 בחירת מסד הנתונים
. מסד הנתונים של Online Checkers ממומש ב-Microsoft Access (קובץ accdb.), עם גישה דרך OleDb בלבד. הבחירה נובעת מכמה סיבות:
. פשטות פיתוח: אין צורך בשרת מסד נתונים נפרד שיש להתקין ולהגדיר. הקובץ הוא קובץ יחיד היושב במחשב, וזה מספיק לפרויקט בקנה מידה זה.
. עמידה בדרישות החלופה: המחוון מצפה למסד נתונים מנורמל עם פעולות SELECT, INSERT, UPDATE ו-DELETE ופרמטרים מאובטחים, ו-Access מספק את כל אלה דרך OleDb.
. ניתן ליצור שאילתות, לקבוע מפתחות זרים ולהשתמש בכל פעולות ה-SQL הסטנדרטיות.

=2 4.2 פירוט הטבלאות (מילון נתונים)
. מסד הנתונים מכיל שלוש טבלאות, וכל אחת מתעדת היבט אחר של המערכת:
. 1. טבלת Users, טבלת המשתמשים.
. מאחסנת את פרטי המשתמשים הרשומים. זוהי הטבלה המשמשת לאימות, ואליה מתייחסות שאר הטבלאות.
. שדות מרכזיים: ID (מפתח ראשי), Username (שם משתמש ייחודי), PasswordHash (תמצית הסיסמה המוצפנת), Email, Role (שחקן או מנהל), Rating (דירוג Elo), Wins, Losses, Draws (סטטיסטיקה), IsBanned (האם חסום), ו-ProfilePicture (תמונת פרופיל בינארית).
img צילום מסך של מבנה טבלת Users ב-Access
. 2. טבלת Games, טבלת המשחקים.
. בכל סיום משחק (מול שחקן אחר או מול הבוט) נוסף רקורד חדש. הטבלה משמשת גם כטבלת קישור בין שני שחקנים.
. שדות מרכזיים: ID (מפתח ראשי), WhitePlayerId ו-BlackPlayerId (מפתחות זרים לטבלת המשתמשים), StartedAt ו-EndedAt (זמני התחלה וסיום), Status (מצב המשחק), EndReason (סיבת הסיום), WinnerId (המנצח), FinalBoard (מצב הלוח הסופי), ו-MoveCount (מספר המהלכים).
img צילום מסך של מבנה טבלת Games ב-Access
. 3. טבלת Moves, טבלת המהלכים.
. בכל מהלך במשחק נוסף רקורד חדש. זה מאפשר צפייה חוזרת (Replay) במשחק שלם.
. שדות מרכזיים: ID (מפתח ראשי), GameId (מפתח זר לטבלת המשחקים), MoveNumber (מספר המהלך), MoverColor (צבע השחקן), FromFile ו-FromRank ו-ToFile ו-ToRank (קואורדינטות המקור והיעד), PathSerialized (מסלול האכילה), IsCapture (האם אכילה), CapturedCount (כמה כלים נאכלו), BecameKing (האם בוצעה הכתרה), Notation (סימון המהלך), ו-BoardAfter (מצב הלוח לאחר המהלך).
img צילום מסך של מבנה טבלת Moves ב-Access

=2 4.3 קשרי הגומלין (ERD)
. הקשרים בין הטבלאות בנויים סביב מזהי המשתמשים והמשחקים:
. Users ו-Games: קשר 1 ל-N. כל משחק מקשר בין שני שחקנים (לבן ושחור), וכל שחקן יכול לשחק משחקים רבים. למעשה טבלת Games מתפקדת כטבלת קישור המייצרת קשר רבים-לרבים בין השחקנים.
. Games ו-Moves: קשר 1 ל-N. לכל משחק שייכים מהלכים רבים, וכל מהלך שייך למשחק יחיד דרך GameId.

=2 4.4 דוגמאות לשאילתות במערכת
. להלן דוגמאות לשאילתות אופייניות במערכת. כולן מוגנות מפני SQL Injection באמצעות פרמטרים (סימן ?).
. שאילתת SELECT עם פרמטר (התחברות), נקראת בכל פעם שמשתמש מתחבר:
code SELECT * FROM Users WHERE Username = ?
. שאילתת INSERT (רישום משתמש חדש):
code INSERT INTO Users (Username, PasswordHash, Email, Role, Rating)
code VALUES (?, ?, ?, ?, ?)
. שאילתת ORDER BY עם TOP (טבלת מובילים), מחזירה את חמישים השחקנים המובילים לפי דירוג:
code SELECT TOP 50 Username, Wins, Losses, Draws, Rating
code FROM Users
code ORDER BY Rating DESC, Wins DESC
. שאילתת UPDATE (עדכון סטטיסטיקות ודירוג בסיום משחק):
code UPDATE Users
code SET Wins = Wins + 1, Rating = ?
code WHERE ID = ?
. שאילתת SELECT עם חיבור (היסטוריית משחקים), מחזירה את כל המשחקים של השחקן עם שמות שני היריבים:
code SELECT g.ID, g.StartedAt, g.WinnerId, g.Status,
code        w.Username AS WhiteName, b.Username AS BlackName
code FROM (Games AS g
code   INNER JOIN Users AS w ON g.WhitePlayerId = w.ID)
code   INNER JOIN Users AS b ON g.BlackPlayerId = b.ID
code WHERE g.WhitePlayerId = ? OR g.BlackPlayerId = ?
code ORDER BY g.StartedAt DESC
. שאילתת SELECT של מהלכים (לצורך צפייה חוזרת):
code SELECT MoveNumber, MoverColor, Notation, BoardAfter
code FROM Moves
code WHERE GameId = ?
code ORDER BY MoveNumber
. שאילתת DELETE (מחיקת משתמש בידי מנהל):
code DELETE FROM Users WHERE ID = ?

# =================== פרק 6 ===================
=1 6. צד שרת

=2 6.1 רכיבי השרת
. המערכת מכילה שני רכיבי שרת, כל אחד עם תחום אחריות:
. שרת WCF (server): השרת המרכזי, המשרת את לקוח ה-WPF ואת אפליקציית ה-MAUI. הוא מבוסס net.tcp לתקשורת מהירה ו-basicHttp לתאימות רחבה, ומתארח כתהליך Console עצמאי שעולה, מאתחל את מסד הנתונים, ויוצר חשבון מנהל ברירת מחדל אם אינו קיים.
. אתר ניהול (WebApplication1): שרת ASP.NET Core המציג את פאנל הניהול בדפדפן ומתחבר לשרת ה-WCF דרך לקוח שנוצר אוטומטית.
. שני הרכיבים חולקים את אותו מסד נתונים, כך שמשתמש שנרשם דרך לקוח אחד יכול להתחבר מכל לקוח אחר עם אותם פרטים.

=2 6.2 שירות WCF ראשי (ICheckersService)
. החוזה של ה-WCF מוגדר בממשק ICheckersService, וכל פעולה מעוטרת ב-[OperationContract]. הממשק מציג את כל הפעולות שהלקוח יכול לקרוא להן, מחולקות לקבוצות:
. אימות: Login (מחזירה טוקן), Register, ו-Logout.
. התאמת יריבים: JoinQueue, LeaveQueue, ו-JoinBotGame.
. מצב המשחק: GetCurrentGame, GetLegalMovesForSquare, ו-GetMoveHistory.
. פעולות במשחק: MakeMove, Resign, OfferDraw, ו-RespondToDraw.
. פרופילים: GetUserProfile, UpdateMyEmail, ChangeMyPassword, ו-UpdateMyProfilePicture.
. סטטיסטיקות: GetTopPlayers, GetMyGameHistory, ו-GetOnlinePlayers.
. ניהול (Admin): AdminGetAllUsers, AdminBanUser, AdminGetRecentGames, ו-AdminGetServerStats.
. האימות מבוסס טוקן: הפעולה Login מחזירה מזהה ייחודי (Guid) שאותו הלקוח שולח בכל קריאה נוספת, וכך השרת מזהה מי הקורא.

=2 6.3 לוגיקה עסקית (GameManager ו-GameSession)
. הלוגיקה של ניהול המשחקים מרוכזת במחלקת GameManager, ומצב של משחק יחיד נשמר במחלקת GameSession.
. ניהול state בזיכרון: כל משחק פעיל נשמר בזיכרון השרת. כך השרת מטפל בכמה משחקים בו-זמנית מבלי לגעת במסד הנתונים בכל מהלך; רק בסיום המשחק התוצאה נשמרת ב-DB.
. התאמת יריבים (Matchmaking): כשמישהו מבקש משחק, השרת בודק אם יש שחקן אחר הממתין בתור (עם שם משתמש שונה). אם כן נוצר משחק חדש; אחרת השחקן נכנס לתור עד שיגיע יריב.
. סנכרון תורות: מצב התור נשמר ב-GameSession. מהלך מאושר רק כשהוא תורו של השחקן ורק לאחר אימות חוקיותו, וכך נמנע מצב שבו שני שחקנים פועלים בו-זמנית.

=2 6.4 תכנות אסינכרוני (Asynchronous Programming)
. הפעולות מול מסד הנתונים והקריאות לשרת מבוצעות באופן אסינכרוני, כדי שהממשק לא ייתקע בזמן ההמתנה לתשובה.
. בצד הלקוח: כל קריאה לשרת מבוצעת על Thread נפרד, וכל עדכון ממשק מתבצע בחזרה על ה-UI Thread.
. בצד השרת: שכבת הגישה לנתונים משתמשת בפעולות אסינכרוניות, כך שבעוד Thread אחד ממתין לתשובת מסד הנתונים, השרת ממשיך לטפל בבקשות של שחקנים אחרים. דוגמה לחתימה אסינכרונית:
code public async Task<User> GetByUsernameAsync(string username)

=2 6.5 שכבת גישת הנתונים (Data Access Layer)
. שכבת ה-DB מורכבת ממחלקה אבסטרקטית BaseDB וממחלקות יורשות UsersDB, GamesDB ו-MovesDB. הירושה מאפשרת שיתוף קוד (פעולות SELECT, INSERT, UPDATE ו-DELETE גנריות), ובו-זמנית מאפשרת לכל יורשת לממש את אופן ההמרה של רשומה לאובייקט מודל.
* BaseDB
. המחלקה האבסטרקטית מספקת: מחרוזת חיבור סטטית הנבנית פעם אחת, אובייקטי OleDb לחיבור ולפקודות, פעולה אבסטרקטית ליצירת אובייקט ריק, פעולה וירטואלית להמרת רשומה לאובייקט, פעולת SELECT גנרית המחזירה רשימה באמצעות פולימורפיזם, ופעולות עדכון גנריות. כל הפעולות תומכות בפרמטרים מוגנים מפני SQL Injection.
* UsersDB
. מוסיפה פעולות לשליפת משתמש לפי שם (להתחברות), שליפת כל המשתמשים (לפאנל הניהול), עדכון פרופיל וסיסמה, שליפת טבלת המובילים, וחסימת משתמש.
* GamesDB
. מטפלת בשמירת משחקים שהסתיימו ובשליפת היסטוריית המשחקים של שחקן, כולל שאילתת חיבור (Join) מול טבלת המשתמשים לשליפת שמות שני השחקנים בבקשה אחת.
* MovesDB
. מטפלת בשמירת כל מהלך ובשליפת רצף המהלכים המלא של משחק, לצורך הצגת צפייה חוזרת.

=2 6.6 אתר הניהול (ASP.NET Razor Pages)
. אתר הניהול הוא רכיב שרת נפרד המספק למנהל ממשק בדפדפן. הוא בנוי ב-ASP.NET Core Razor Pages ומתחבר לשרת ה-WCF דרך לקוח שנוצר אוטומטית. האתר כולל לוח בקרה עם נתוני השרת, מסך ניהול משתמשים (כולל חסימה), ומסך צפייה במשחקים אחרונים. הגישה אליו מוגנת באמצעות עוגיית התחברות (Cookie Authentication) ובדיקת הרשאת מנהל.

=2 6.7 תקשורת בזמן אמת (Polling)
. בשונה ממערכות המבוססות דחיפה (Push), עדכון מצב המשחק בלקוחות מבוסס דגימה (Polling): לקוח ה-WPF ולקוח ה-MAUI שואלים את השרת על מצב המשחק במרווחי זמן קצרים (כחצי שנייה), ומציגים את המצב המעודכן. גישה זו פשוטה ליישום, אינה דורשת חיבור קבוע, ומתאימה לקצב של משחק תורות.

=1 7. צד לקוח

=2 7.1 לקוח WPF Desktop
. עיצוב הממשק: לקוח ה-WPF מעוצב בערכת צבעים אחידה ונקייה, עם סגנונות גלובליים המוגדרים בקובץ App.xaml ומאפשרים שימוש חוזר ואחידות ויזואלית בכל המסכים.

=2 7.3 לקוח MAUI (Android ו-Windows)

# =================== פרק 8 ===================
=1 8. אבטחה והגנה על נתונים

=2 8.1 הצפנת סיסמאות עם PBKDF2
. סיסמאות הן הנתון הרגיש ביותר במערכת. אסור לאחסן אותן בטקסט גלוי, ואסור גם להצפין אותן באלגוריתם הפיך, כי אם מסד הנתונים נפרץ, מישהו יוכל לפענח אותן בחזרה.
. הפתרון הנכון הוא תמצית (Hash) חד-כיוונית, פונקציה שלא ניתן להפוך. במערכת השתמשתי ב-PBKDF2 עם פונקציית הגיבוב SHA-256. לכל סיסמה נוצר Salt אקראי, והתמצית מחושבת במספר רב של סבבים, מה שמקשה מאוד על ניסיונות פיצוח.
code public static string Hash(string password)
code {
code     byte[] salt = RandomNumberGenerator.GetBytes(16);
code     var pbkdf2 = new Rfc2898DeriveBytes(password, salt, 60000, HashAlgorithmName.SHA256);
code     byte[] hash = pbkdf2.GetBytes(32);
code     return $"{60000}.{Convert.ToBase64String(salt)}.{Convert.ToBase64String(hash)}";
code }
. התמצית נשמרת בפורמט הכולל את מספר הסבבים, ה-Salt וה-Hash. בעת ההתחברות מחושבת תמצית הסיסמה שהוזנה ומושווית לתמצית השמורה בהשוואה בזמן קבוע (Constant-Time Comparison), מה שמונע התקפות תזמון (Timing Attacks).

=2 8.2 הגנה מ-SQL Injection
. SQL Injection היא אחת ההתקפות הנפוצות על מסדי נתונים. היא מתרחשת כשמכניסים קלט משתמש ישירות לתוך מחרוזת SQL, ומשתמש זדוני יכול להזריק תוכן שמשנה את משמעות השאילתה.
. ההגנה היחידה האמיתית היא שימוש בפרמטרים (Parameterized Queries). כל שאילתה במערכת משתמשת בפרמטר OleDb עם סימן ?:
code // נכון, מוגן מ-SQL Injection:
code string sql = "SELECT * FROM Users WHERE Username = ?";
code command.Parameters.AddWithValue("?", username);
code // שגוי, פגיע ל-SQL Injection:
code // string sql = "SELECT * FROM Users WHERE Username = '" + username + "'";
. הספק של OleDb מתייחס לערך כפרמטר ולא כחלק מתחביר ה-SQL, ולכן גם אם המשתמש מזין תוכן זדוני, הוא נבדק כשם משתמש בלבד ואינו משנה את השאילתה.

=2 8.3 ניהול אימות מבוסס טוקן
. האימות במערכת מבוסס טוקן: בעת התחברות מוצלחת מייצר השרת מזהה ייחודי (Guid) ושומר אותו יחד עם שם המשתמש המשויך. הלקוח מקבל את הטוקן ושולח אותו בכל קריאה נוספת. השרת מאמת את הטוקן בכל פעולה, מאתר את המשתמש המשויך, ורק אז מבצע את הבקשה. טוקן שאינו תקין נדחה מיד. גישה זו שומרת על השרת חסר-מצב מבחינת זהות הלקוח ומאפשרת ניתוק נקי בעת Logout.

=2 8.4 אכיפת חוקים בצד השרת
. שכבת אבטחה חשובה נוספת היא אכיפת כל לוגיקת המשחק בצד השרת בלבד. הלקוח מציג את הלוח ושולח את המהלך המבוקש, אך תקינות המהלך נבדקת אך ורק בשרת על-ידי CheckersEngine. כך שחקן אינו יכול לזייף אכילה, לדלג על אכילת חובה, להזיז כלי של היריב או לבצע מהלך לא חוקי, גם אם ישנה את קוד הלקוח.

=2 8.5 הגנת Admin
. פאנל הניהול מוגן בשתי שכבות: בצד הלקוח, מסך הניהול נחשף רק למשתמש שהרשאתו Admin; ובצד השרת, פעולות הניהול (כגון חסימת משתמש) מאמתות את הטוקן ובודקות שלמשתמש המבצע יש הרשאת מנהל לפני הביצוע. כך לא ניתן לעקוף את ההגנה דרך פנייה ישירה לשרת.

# =================== פרק 9 ===================
=1 9. תהליכים מרכזיים במערכת

=2 9.1 תהליך התחברות
. התחברות היא התהליך הראשון שכל משתמש עובר. השלבים:
. המשתמש מזין שם משתמש וסיסמה במסך ההתחברות.
. הלקוח שולח את הפרטים לשרת באמצעות הפעולה Login.
. השרת קורא ל-UsersDB לשליפת המשתמש לפי שם, באמצעות שאילתה עם פרמטר.
. אם המשתמש קיים, השרת מאמת את הסיסמה באמצעות PasswordHasher (PBKDF2).
. אם הסיסמה תקינה, השרת מייצר טוקן (Guid), שומר אותו, ומחזיר אותו ללקוח.
. הלקוח שומר את הטוקן ועובר ללובי.

=2 9.2 תהליך התאמת משחק (Matchmaking)
. בלחיצה על חיפוש משחק, מנהל ההתאמה בשרת מנהל את התור:
. הלקוח קורא לפעולה JoinQueue.
. השרת בודק אם כבר ממתין שחקן אחר בתור (עם שם שונה).
. אם כן, שני השחקנים מוצאים מהתור, נוצר משחק חדש, ושני הצדדים מקבלים הודעה שהמשחק התחיל.
. אם לא, השחקן מצטרף לתור וממתין.
. בכל רגע השחקן יכול לבטל את החיפוש באמצעות LeaveQueue.

=2 9.3 תהליך פתיחת משחק
. בשונה ממשחקים שדורשים הצבת כלים, בדמקה הכלים ניצבים במצב פתיחה קבוע. לאחר שנמצא יריב (או מיד, אם נבחר משחק מול הבוט):
. השרת יוצר מצב לוח התחלתי עם הכלים בעמדותיהם.
. השרת מגריל מי מתחיל ושולח לשני הצדדים את מצב הלוח הראשוני.
. שני הצדדים מועברים למסך המשחק, והשחקן שתורו ראשון מתחיל.

=2 9.4 תהליך ביצוע מהלך
. ביצוע מהלך הוא הפעולה המרכזית במשחק. כאשר השחקן בוחר כלי ויעד ולוחץ לביצוע:
. הלקוח קורא לפעולה MakeMove עם מסלול המהלך (משבצת מקור ומשבצות היעד).
. השרת מוודא שזהו תורו של השחקן.
. השרת מעביר את המסלול ל-CheckersEngine, המחשב את כל המהלכים החוקיים ובודק אם המהלך שנשלח נמצא ביניהם.
. אם המהלך אינו חוקי, הוא נדחה והלוח אינו משתנה.
. אם המהלך חוקי, השרת מחיל אותו על הלוח: מזיז את הכלי, מסיר את הכלים שנאכלו לאורך המסלול, ומבצע הכתרה אם הכלי הגיע לשורה האחורית.
. השרת מעביר את התור לצד השני, שומר את המהלך בטבלת Moves, ובודק אם המשחק הסתיים (אם לאחד הצדדים אין כלים או אין מהלך חוקי).
. אם המשחק הסתיים, השרת מעדכן את התוצאה, מחשב את שינוי ה-Elo, ושומר את המשחק.

=2 9.5 אלגוריתם היריב הממוחשב (Bot)
. היריב הממוחשב מיושם במחלקת BotEngine. בתורו הוא פונה ל-CheckersEngine לקבלת רשימת כל המהלכים החוקיים שלו, ובוחר מתוכם מהלך. הבחירה אינה אקראית לחלוטין: הבוט מעדיף מהלכים המובילים להכתרת מלך, ובכך משחק בצורה מעט חכמה יותר. מכיוון שכל המהלכים מגיעים מאותו מנוע חוקים שמשמש את השחקנים האנושיים, הבוט לעולם אינו מבצע מהלך לא חוקי ומכבד את חובת האכילה.

=2 9.6 תהליך הניתוק
. ניתוק יכול לקרות בכמה אופנים:
. ניתוק יזום: המשתמש לוחץ על התפטרות (Resign). הצד השני מקבל הודעת ניצחון, והתוצאה נשמרת.
. סגירת חלון: בלקוח ה-WPF, בעת סגירת החלון נשלחת הודעת עזיבה לשרת לפני הסגירה.
. ניתוק רשת או קריסה: אם לקוח מפסיק להגיב, טיימר ה-StaleSweep בשרת מזהה זאת לאחר פרק זמן מוגדר, מסיים את המשחק לטובת היריב, ומטיל קנס דירוג על הנוטש.

# =================== פרק 10 ===================
=1 10. בדיקות ותסריטי שימוש

=2 10.1 בדיקות ידניות שביצעתי
. במהלך הפיתוח ביצעתי בדיקות ידניות שיטתיות לכל תרחיש. הבדיקות חולקו לקטגוריות:
. בדיקות אימות וגישה: רישום עם פרטים תקינים ולא תקינים, התחברות עם סיסמה נכונה ושגויה, ניסיון גישה לפאנל ניהול ללא הרשאה.
. בדיקות מנוע המשחק: ביצוע מהלך פשוט, ניסיון מהלך לא חוקי, אכילה רגילה, אכילה כפולה, אכילת חובה, והכתרת מלך.
. בדיקות משחק רב-משתתפים: התאמת שני שחקנים, ביצוע מהלכים לסירוגין, הצעת תיקו והתפטרות, וסיום משחק עם עדכון דירוג.
. בדיקות פאנל ניהול: צפייה ברשימת המשתמשים, חסימת משתמש, וצפייה במשחקים אחרונים.

=2 10.2 בדיקות עומס
. בנוסף לבדיקות הפונקציונליות, בחנתי כמה משחקים יכולים לרוץ בו-זמנית:
. כמה משחקים פעילים במקביל רצו ללא בעיות, והשרת הגיב בזמן.

=2 14.3 דוגמת קוד, מנוע המשחק (יצירת מהלכים)

code {

code     // סריקת כל הכלים של הצד התורן
code     for (int f = 0; f < 8; f++)

code               GenerateSlideMovesFrom(board, new Square(f, r), p, slides);

=2 14.4 דוגמת קוד, הצפנת סיסמאות (PasswordHasher)
. מחלקת ההצפנה משתמשת ב-PBKDF2 עם SHA-256, Salt אקראי, ומספר רב של סבבים:
code public static string Hash(string password)
code {
code     byte[] salt = RandomNumberGenerator.GetBytes(16);
code     var k = new Rfc2898DeriveBytes(password, salt, 60000, HashAlgorithmName.SHA256);
code     byte[] hash = k.GetBytes(32);
code     return $"{60000}.{Convert.ToBase64String(salt)}.{Convert.ToBase64String(hash)}";
code }
code
code public static bool Verify(string password, string stored)
code {
code     string[] parts = stored.Split('.');
code     int iters   = int.Parse(parts[0]);
code     byte[] salt = Convert.FromBase64String(parts[1]);
code     byte[] hash = Convert.FromBase64String(parts[2]);
code     var k = new Rfc2898DeriveBytes(password, salt, iters, HashAlgorithmName.SHA256);
code     byte[] test = k.GetBytes(32);
code     return CryptographicOperations.FixedTimeEquals(test, hash);
code }
